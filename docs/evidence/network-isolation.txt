=== CNI-SPECIFIC FINDING WORTH AN ENGINEERING-NOTES MENTION: DNS ClusterIP vs podSelector ===
This is the non-obvious part of getting NetworkPolicy working on k3s, and it
fails silently.

Pods do not query the CoreDNS pod. /etc/resolv.conf points at the kube-dns
*Service* ClusterIP (10.43.0.10 on this cluster), so the DNS packet leaves the
pod addressed to a Service IP, not a pod IP.

A DNS allow-rule written the obvious way -- egress to pods matching
`k8s-app: kube-dns` in namespace kube-system -- does NOT work here. This CNI
evaluates egress policy BEFORE DNAT, so a podSelector cannot match a ClusterIP
destination. With only that rule applied:

  nslookup postgres  ->  *** can't find postgres.svc.cluster.local: NXDOMAIN

while a query sent directly to the CoreDNS *pod* IP (10.42.1.37) got through
fine, which is what proved the rule was matching the wrong thing rather than
DNS being broken generally.

The fix is to allow BOTH destinations on port 53 UDP/TCP:
  - podSelector k8s-app=kube-dns  (correct on a post-DNAT CNI, and covers
                                  direct-to-pod DNS)
  - ipBlock for the kube-dns ClusterIP 10.43.0.10/32  (required here)

Re-derive that address if the service CIDR changes:
  kubectl get svc kube-dns -n kube-system -o jsonpath='{.spec.clusterIP}'

Worth stressing: while DNS was broken in that window, EVERY pod still reported
1/1 Ready. Readiness probes passed because they were served over
already-established TCP connections and the probe endpoint did not need a fresh
name lookup. A pod restart during that window would have failed to start. So
"all pods Ready" is not evidence that a NetworkPolicy apply was correct -- the
explicit reachability tests above are.

=== k3s DOES enforce NetworkPolicy (contrary to the common assumption) ===
The widespread claim is that k3s/flannel does not enforce NetworkPolicy at
default because plain flannel has no policy engine. That is wrong for k3s: k3s
runs the policy controller inside the k3s agent unless started with
--disable-network-policy, and no separate kube-router/flannel pod appears in
kube-system, which is expected rather than a sign of a missing component.

Verified empirically rather than assumed. With only default-deny-all plus the
DNS rule applied, frontend->postgres, frontend->redis and backend->postgres all
became unreachable while all pods stayed Ready. The policy is genuinely being
enforced.

kubelet -> pod probe traffic is exempt on this cluster: pods stayed 1/1 Ready
across the whole staged rollout, so no explicit allow for the kubelet is needed
here. That was the highest-risk item in the change and it did not materialise.

=== HOW THIS WAS APPLIED SAFELY ===
The full 8-policy file was not applied in one shot. It was staged:

  1. default-deny-all + allow-dns-egress only. Waited 30s, confirmed all pods
     stayed 1/1 Ready (kubelet probe risk retired) and confirmed traffic was
     actually being blocked (enforcement proven, not assumed).
  2. Found and fixed the DNS ClusterIP problem above.
  3. Applied the remaining 6 allow rules, then re-ran every check.

=== COMPOSE EQUIVALENT (still the reference topology) ===
Both compose.yaml and compose.prod.yaml define:

  network edge:     driver bridge, internal=false
  network internal: driver bridge, internal=true

  postgres -> ['internal']      redis   -> ['internal']
  backend  -> ['edge', 'internal']
  frontend -> ['edge']

In Compose the frontend is attached only to `edge` and has no route to
`internal`, where Postgres lives. The NetworkPolicy now reproduces that same
result at the Kubernetes layer, by omission rather than by attachment: no
policy grants the frontend egress to postgres or redis, so default-deny
applies to it.

=== RELATED LIMITATION (not a policy issue) ===
The Ingress is served inside the cluster network only. This k3d cluster was
created without `-p 80:80@loadbalancer`, so traefik's LoadBalancer addresses
(172.22.0.2-5) are not reachable from the WSL host or a browser. The Ingress
itself is healthy and routes correctly; host-side access needs the port
mapping when the cluster is recreated for a clean final test.
